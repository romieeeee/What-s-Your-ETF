# 1단계: 시뮬레이션 계산 흐름과 측정 시나리오

## 이 단계의 목적

성능을 개선하기 전에 사용자의 입력이 어떤 경로로 계산까지 전달되는지 확인하고, 개선 전후를 같은 조건으로 비교할 수 있도록 측정 시나리오를 고정한다.

이 단계에서는 최적화 코드를 적용하지 않는다.

## 실제 코드 흐름

투자 금액 입력을 기준으로 한 흐름은 다음과 같다.

1. 화면에서 투자 금액을 입력한다.
2. `SimulationViewModel.onAmountChanged()`가 화면 상태의 금액을 갱신한다.
3. `triggerCalculation()`이 기존 `calcJob`에 취소를 요청한다.
4. 새 코루틴이 시작되고 300ms 동안 기다린다.
5. 300ms 안에 다음 입력이 들어오면 대기 중인 계산은 취소된다.
6. 입력값과 ETF 비중이 유효하면 가격 이력과 펀더멘털을 준비한다.
7. `RunSimulationUseCase`가 백테스트와 가중 펀더멘털 계산을 실행한다.
8. 계산 결과를 UI 모델로 변환한 뒤 `UiState.Success`로 화면에 전달한다.

관련 코드:

- `SimulationViewModel.onAmountChanged()`
- `SimulationViewModel.triggerCalculation()`
- `RunSimulationUseCase.invoke()`
- `CalculateBacktestUseCase.invoke()`
- `CalculateWeightedFundamentalsUseCase.invoke()`
- `SimulationUiModel.toUiModel()`

## 코드에서 확인한 중요한 점

### 1. 300ms 대기는 디바운스 역할을 한다

사용자가 빠르게 연속 입력하면 각 글자마다 계산하지 않고 마지막 입력 이후 300ms가 지나야 계산을 시작한다.

### 2. `cancel()`은 즉시 중단 명령이 아니라 취소 요청이다

코루틴이 `delay(300)`에서 기다리는 동안에는 취소가 잘 반영된다. 하지만 계산이 시작된 뒤 실행되는 백테스트 코드는 동기식 반복문이며, 현재 명시적인 취소 확인 지점이 없다. 따라서 계산 도중 새 입력이 들어왔을 때 이전 계산이 실제로 언제 끝나는지는 로그나 트레이스로 측정해야 한다.

### 3. 실행 스레드를 바꾸는 코드가 보이지 않는다

`viewModelScope.launch` 안에서 계산하며 `Dispatchers.Default`나 `withContext` 사용은 확인되지 않았다. 기본 동작상 메인 스레드에서 시작할 가능성이 높지만, 최종 판단은 측정 결과로 확정한다.

### 4. 비중 입력은 첫 측정 입력으로 부적합하다

ETF 비중 합계가 100이 아니면 실제 시뮬레이션 계산 전에 반환한다. 슬라이더를 움직이는 대부분의 순간에는 무거운 계산이 실행되지 않을 수 있어 반복 계산 문제를 관찰하기 어렵다.

## 첫 측정 입력

첫 측정은 **투자 금액 연속 입력**으로 한다.

선택 이유:

- 숫자 한 글자마다 `onAmountChanged()`가 호출된다.
- ETF 비중과 투자 기간을 미리 유효하게 만들면 각 입력이 같은 계산 경로를 탄다.
- 빠른 입력, 300ms보다 긴 입력 간격, 계산 중 재입력을 비교하기 쉽다.

## 고정 데이터와 조건

- 빌드: 현재 Debug + Fake Repository
- ETF 수: 6개
- ETF 비중 합계: 100%
- 가격 이력: Fake Repository가 제공하는 약 3년치 영업일 데이터
- 투자 기간: 36개월
- 투자 방식: 우선 거치식으로 고정
- 입력 전 상태: 최초 계산 결과가 화면에 표시된 상태
- 입력값: 기존 금액을 지운 뒤 `10000`을 입력 (`만원` 단위이므로 1억원)
- 탐색 반복: 실제 UI 입력 간격을 확인하기 위해 같은 조건으로 3회
- 공식 측정: warm-up 5회 후 최소 20회

이 조건은 최대 부하 시험이 아니라 현재 Fake 데이터에서 누구나 반복할 수 있는 대표 시나리오다.

기존 후보였던 `10000000`은 화면의 허용 범위를 초과하므로 사용하지 않는다.

## 자동 입력 재현 방법

- Debug 전용 `SimulationAmountInputDriver`가 `1 → 10 → 100 → 1000 → 10000`을 순서대로 전달한다.
- 입력 간격은 driver에 인자로 전달하며, 실제 UI 관찰 전에 임의의 공식 수치로 고정하지 않는다.
- debounce와 최신 결과 우선 처리는 coroutine 가상 시간 테스트로 검증한다.
- 실제 성능 시간은 Android instrumentation harness에서 실제 시간과 Main dispatcher를 사용해 측정한다.
- 공식 측정에서는 입력값, 순서, 간격, fixture, warm-up 횟수와 측정 횟수를 동일하게 유지한다.

## 처음 수집할 지표

1. 금액 입력 이벤트 수와 실제 계산 시작·완료 횟수
2. 이전 계산 취소 요청 횟수와 실제 종료 시점
3. 전체 및 단계별 계산 소요 시간
4. 마지막 입력부터 `UiState.Success` 반영까지 걸린 시간
5. 계산 시작과 종료가 실행된 스레드 이름

## 병목 판정과 후보 전환 기준

- 동일 조건의 반복 측정에서 같은 현상이 재현되어야 한다.
- median 차이가 실행 간 자연 변동 폭과 비슷하면 병목이나 개선으로 판단하지 않는다.
- 취소 요청 이후 이전 calculationId가 종료되기까지의 지연이 반복적으로 관찰될 때만 cancellation 후보를 유지한다.
- 계산이 Main Thread에서 실행되고 사용자 입력 전달이나 상태 갱신을 지연시키는 근거가 있을 때만 Main Thread 후보를 유지한다.
- cancellation 가설이 기각되면 Main Thread 점유를 확인하고, 두 후보 모두 의미가 없으면 반복 변환 후보까지만 확인한다.
- 시뮬레이션 영역의 우선 후보 두 개에서 의미 있는 문제가 없으면 결과를 기록하고 다른 사용자 흐름으로 이동한다.

## 현재 가설

아래 내용은 아직 결론이 아니다.

- 300ms 안의 빠른 입력은 대기 단계에서 취소되어 마지막 계산만 실행될 가능성이 높다.
- 계산이 시작된 후에는 동기식 반복문에 취소 확인 지점이 없어 이전 계산이 끝날 때까지 새 계산이 지연될 수 있다.
- 백테스트 계산이 메인 스레드에서 실행된다면 입력이나 화면 갱신이 끊길 수 있다.
- 적립식 계산에는 중간 결과를 만든 뒤 다시 비슷한 계산을 수행하는 것으로 보이는 구간이 있어 비용이 중복될 가능성이 있다.

가설은 다음 단계의 계측 결과로 검증한다.

## 사용자 확인 시나리오

1. 시뮬레이션 화면에서 ETF 6개를 선택한다.
2. 비중 합계를 100%로 맞춘다.
3. 기간을 36개월, 투자 방식을 거치식으로 설정한다.
4. 첫 결과가 표시될 때까지 기다린다.
5. 투자 금액을 지우고 `10000`을 평소 속도로 입력한다.
6. 입력 중 멈춤, 로딩 고착, 이전 값의 결과가 잠깐 표시되는지 관찰한다.

이 수동 확인은 실제 입력 간격을 관찰하고 시나리오를 보정하기 위한 것이다. 공식 Before/After 수치는 자동 입력 driver와 동일한 측정 harness로 수집한다.

## 1단계 완료 기준

- 계산 경로를 코드 기준으로 설명할 수 있다.
- 반복 가능한 입력과 데이터 조건이 정해졌다.
- 자동 입력 재현 방법이 정해졌다.
- 측정할 지표와 검증할 가설이 정해졌다.
- 병목 판정 및 후보 전환 조건이 정해졌다.
- 최적화 코드는 아직 적용하지 않았다.
